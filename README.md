# Agent Traffic Control

A coordination toolkit of 123 [Claude Code](https://claude.com/claude-code) skills — plus one installable hook — for **running multiple parallel sessions against the same repo without collisions, stranded work, or rebase loops**: issue-pickup claim protocol, worktree & session-isolation pitfalls, parallel-PR conflict recovery, subagent-integrity edge cases, and the squash/merge mechanics that bite when multiple PRs converge on the same branch.

[![last commit](https://img.shields.io/github/last-commit/wan-huiyan/agent-traffic-control)](https://github.com/wan-huiyan/agent-traffic-control/commits)

## When to reach for this toolkit

- You routinely run **2+ Claude Code sessions in parallel** against the same repo (worktrees, separate terminals, scheduled overnight loops, or sandbox + main).
- You've seen **two sessions independently start work on the same issue**, **PRs collide on rebase**, **subagent reports look complete but the PR never merged**, **a worktree's index goes corrupt right after committing in a sibling**, or **GitHub squash-merge auto-closes only one issue out of three you listed in the PR body**.
- You want **upstream prevention** at the issue-pickup boundary plus **downstream recovery** for the failure modes that still slip through.

## Installation

```bash
# Add the marketplace
/plugin marketplace add wan-huiyan/agent-traffic-control

# Install the plugin — one shot, gets all 123 skills
/plugin install agent-traffic-control@wan-huiyan-agent-traffic-control
```

Installing the plugin gets you the skills. The `resume-gate` and `leg-guard` **hooks are not installed by this** and never fire until you run their installers by hand — see [The hook](#the-hook--resume-gate) and [leg-guard](#the-hook--leg-guard) below.

This is a single multi-skill plugin (modeled on `superpowers`), not a marketplace of individual plugins. One install gets you the full `before / during / after / orchestrator-aware / merge-mechanics` arc; you can't pick-and-choose per-skill via `/plugin install`. If you only want one or two of these skills, copy them directly into `~/.claude/skills/<skill-name>/` instead.

## The hook — `leg-guard`

**One heavy local test leg at a time, machine-wide.** A `PreToolUse` hook on `Bash` that refuses
to start a heavy test suite while another session's is already running, names the peer, and offers
an explicit `DR_LEG_FORCE=1` override.

```
python3 plugins/agent-traffic-control/hooks/leg-guard/install.py --check
python3 plugins/agent-traffic-control/hooks/leg-guard/install.py
```

It exists because the advisory form of this rule did not hold.
[`parallel-gate-legs-killed-for-memory-count-cannot-see-ram`](plugins/agent-traffic-control/skills/parallel-gate-legs-killed-for-memory-count-cannot-see-ram/SKILL.md)
has said *"test for ZERO, not for under N"* and *"put the guard inside the command that starts the
leg"* since 2026-09-17. On 2026-09-22, **four sessions ran the same pytest suite concurrently** on
one laptop at load average 14; one leg was killed at 537 s with `exit=-15` and wrote no measurement
at all. Nobody broke a rule they knew about — they had not consulted it. **A rule that costs
nothing to skip is not a rule**, which is the whole argument for a hook over a paragraph.

It blocks rather than warns, because warning is what the skill already did in words. It counts
process LINES rather than a bare count, collapses xdist workers onto their parent, excludes wrapper
shells, matches case-insensitively, and tests for **zero** — every one of those forced by a
measurement in that skill, where one leg reads as 2 and the same machine reports 5, 2 or 7
depending on one letter's case. It **fails open** on any internal error, because it runs on every
`Bash` call and a crashing hook that blocked everything would be far worse than one that blocked
nothing. It never kills a peer's leg, and it never judges memory — a process count is a
CPU-and-contention rule that cannot see RAM, so free memory is printed as context and decides
nothing.

Full reasoning, the measured cost (~28 ms per ordinary `Bash` call) and the two defects its own
mutation check found are in
[its README](plugins/agent-traffic-control/hooks/leg-guard/).

## The hook — `resume-gate`

Every skill in this toolkit fires because a human, or the model, notices something and reaches for
it. One failure mode gives nobody anything to notice: **a subagent killed mid-run leaves its partial
output sitting in the parent's transcript, and a later session resuming that branch reads it as a
finished, reviewed result and ships it.**

[**resume-gate**](plugins/agent-traffic-control/hooks/resume-gate/) is the trigger for that case —
a `SessionStart:resume` detector plus a `PreToolUse` gate:

- On resume it names every subagent whose work the interrupted session never assessed, under two
  signatures: the harness's own partial-output notice for a **synchronous** subagent, and a
  non-`completed` task-notification status for an **asynchronous** one. The async half is the one
  that matters — 81 of 181 measured Agent calls return only `Async agent launched successfully`, so
  no partial-output notice ever reaches the parent no matter what happens to the subagent.
- Until those are re-verified, all seven ship conditions — `git push`, `git -C <path> push`,
  `gh pr merge`, `gh pr create`, `gh pr edit` (which covers `--add-label auto-deploy`, a deploy with
  no push or merge verb in the command at all), `gh api` (a REST-API merge), `gh release create` —
  plus the configured publish tools get `permissionDecision: "ask"`. A human keypress, not an
  auto-deny the model can retry past. **Not commits.**
- It warns **once per interruption**, not once per resume: the detector writes a mark into the
  transcript carrying what it found, and clears that mark when nothing is outstanding.

**It is opt-in and installed by hand** — `python3 install.py` after copying it to a stable
directory. It is deliberately *not* registered as a plugin-native hook, so installing or updating
this plugin never changes how your sessions behave until you choose to run the installer. The
installer **refuses to run from a plugin cache, a worktree, or `/tmp`**, because the hook config
stores an absolute path and a `PreToolUse` hook whose script has vanished exits 2 — which blocks the
tool call, so every push on the machine fails with nothing naming the cause. That happened once
already; see [DESIGN.md](plugins/agent-traffic-control/hooks/resume-gate/DESIGN.md), which also
records the two earlier designs that were built, measured and rejected.

94 tests, plus a committed mutation harness (`tests/mutation_check.py`, 38 mutations) so its own
test-quality claim can be re-run rather than believed. Fixtures are generated, not captured —
`make_fixtures.py` builds them deterministically and a test regenerates and compares byte for byte.
Both run in CI.

## When NOT to reach for this toolkit

- **Routine single-session work** with no coordination or research-retrospective need. The protocols are overhead with no benefit.
- **Cross-team coordination across separate repos** (real merge-queue territory) — out of scope.


## Research Garden and Learning Loop

Use `Research Garden` (`research-lane-coordinator`) to coordinate investigations and evidence across independent lanes. It separates research direction from PR-queue operations and can escalate reasoning within a bounded budget when useful; no single model is mandatory, and the skill grants no new permissions beyond the current user authorization.

Use `Learning Loop` after a Garden finding, or after any similarly evidenced correction. It checks the cause, makes one narrow change, tests the change against the relevant regression, then keeps the guidance if it holds or removes the bad rule if the evidence rejects it. The loop is generic across coding, research, design, and operations. Memory hygiene may audit its private correction records, but it is optional, and no background automation or global-memory rewrite is installed. Traffic control owns the parallel filesystem and PR safety layer, including release handoffs; Garden owns investigations and evidence, while Learning Loop owns the tested correction.

Examples: “Coordinate measurement, candidate-construction and evaluation lanes for this prototype. Keep their baselines comparable, preserve negative results, and hand only qualified changes to the queue coordinator.” “The latest evidence contradicts this rule. Isolate the cause, make the smallest correction, run the regression checks, and retire the rule if it does not hold.”

For a direct Codex installation, install the `research-lane-coordinator`, `learning-loop`, and `fan-out-cost-control` directories together as siblings in the host's skills directory so their relative links resolve. The first two have Codex display metadata; the stable invocation names remain unchanged. Claude users receive them through the existing plugin installation. Keep project-specific queue policies and incident evidence outside the public skills.

## Version history

- **v1.46.0** (2026-09-22) — **The concurrency rule became a hook, because the paragraph form of it demonstrably did not hold.** No new skill; one skill extended, one hook added. **What happened.** `parallel-gate-legs-killed-for-memory-count-cannot-see-ram` has said *"test for ZERO, not for under N"* and *"put the guard inside the command that starts the leg"* since 2026-09-17. Six days later, four sessions ran the same `prototype` pytest suite concurrently on one laptop — two full suites, one with four xdist workers, plus a six-file subset and a four-leg loop — at load averages 8.40 / 14.01 / 11.44. One leg was killed at 537 s with `exit=-15`, writing no JUnit XML and no collected count. The session that lost it had not consulted the skill before starting, and neither had the others. **The signature was the memory kill's, and the cause was not.** System-wide memory read 81% free. `-15` is SIGTERM, which an OS memory kill does not normally send — and the skill's own note already warns that a `-9` beside a timeout is not evidence of memory either, so both directions of that inference are wrong. The skill now carries that counter-case explicitly, because the remedy for a memory kill is the wrong remedy here and a reader hitting `exit=-15` lands on that skill first. **The better detector was not the log.** `gate_receipt.py check` refused the run with four independent statements that no measurement existed — `leg-red`, `zero-collected`, `deselected-unmeasured`, `evidence-missing` — where the leg table showed one ambiguous number. Recorded as: if your harness writes a receipt, read its refusal before the log. **NEW: `hooks/leg-guard`.** A `PreToolUse` hook on `Bash`. Blocks rather than warns, since warning is what the skill already did; `DR_LEG_FORCE=1` overrides, so a stuck peer leg can never deadlock the machine and an override is visible in the transcript where forgetting is not. It reads process LINES with parentage rather than a bare count, collapses xdist workers onto their parent, excludes wrapper shells explicitly, matches case-insensitively, and tests for **zero** — each forced by a measurement in that skill, where one leg reads as 2 and one letter's case makes the same machine report 5, 2 or 7. It **fails open**: it runs on every `Bash` call, exit codes other than 2 do not block anyway, so refusing could never be made reliable through failure, and a crashing hook that blocked everything would be far worse than one that blocked nothing. It never kills a peer's leg — that destroys a measurement its owner reads as red — and never judges memory, printing free memory as context only. **Verified live, not just in fixtures**: blocked against four real peer legs, allowed the same command under the override, left `git status` untouched, and cost ~28 ms per ordinary `Bash` call and ~90 ms on a leg. **Its mutation check found two real defects on its first run.** A **vacuous test**: the wrapper-shell fixture lacked the `python -m pytest` text, so it passed without ever reaching the filter it was named after — it now asserts the fixture still matches the peer pattern first. And a **missing test entirely**: nothing covered the hook excluding its own process chain, so it could have counted itself as a peer and refused every leg on an idle machine. Thirteen cases, six mutations, all caught. Like resume-gate's check since v1.27.0, it refuses rather than reporting a vacuous pass when pytest is unavailable, verified under an interpreter with pytest blocked. **Both new gates are named in `ci.yml` AND `.githooks/pre-push`** — `check_hook_parity()` failed the first attempt for exactly that omission, which is the check from v1.27.0 doing its job. A worktree isolates the SOURCE TREE and nothing else — a simulator install keyed by bundle id, a build cache keyed by project path, a tool cache keyed by version string and a dev server keyed by port are all shared by every worktree on the machine. Three properties make it expensive: the failure is CONFIDENT (detailed, plausible, wrong — not an error); detection-by-counting cannot see a stale *install*, because those cases do run; and the remedy is where the bug gets created, since copying and syncing are what you reach for to repair staleness. Worked example: one machine, ten worktrees, one iOS app, the same shape three times — `** TEST SUCCEEDED **` over zero executed cases, a simulator serving an app `xcodebuild` believed it had replaced (through a `clean` AND a `simctl erase`) that produced seven failing suites plus a layout guard reporting the exact values of a build reverted an hour earlier, and a tool cache whose repair reintroduced the defect being repaired. Also adds the missing warning to `prove-test-failures-pre-existing-via-clean-worktree`: its method is sound and was used successfully the same day (13 failures proved pre-existing, byte-identical sets), but its BASELINE is exposed to this pattern — one attempt silently ran test bundles built by two *other* worktrees, caught only because the failure messages carried their compiled-in source paths.
